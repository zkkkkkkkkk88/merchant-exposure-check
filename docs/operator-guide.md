# 商家曝光检测操作手册

## 1. 启动服务

复制 `.env.example` 为 `.env`，确认 PostgreSQL 账号后启动数据库、API 和网页：

```powershell
docker compose up --build db api web
```

需要执行火山方舟联网检测时，再启动 worker：

```powershell
docker compose --profile scans up worker
```

首次启动后执行迁移和示例初始化：

```powershell
docker compose exec api alembic upgrade head
docker compose exec api python -m scripts.seed_demo
```

示例命令可重复执行，不会重复创建 O'eat 商家、问题库或演示检测。

## 2. 无 API 凭据的人工模式

在问题库批准待检测问题，创建 adapter 为 `manual` 的检测，再通过检测详情导入逐题原始回答和公开来源。人工模式不读取 `ARK_API_KEY`，适合试用、回放或固定样本验证。不要编辑已经保存的原始回答；需要修正时，新建一次检测。

## 3. 配置火山方舟联网模式

只在 API 与 worker 的服务器环境中设置 `ARK_API_KEY` 和 `ARK_MODEL`。不要把密钥写入网页环境变量、浏览器代码、提交记录或截图。创建 `ark` 检测后，由 worker 执行；页面展示 queued、running、completed、partial 或 failed 状态。失败问题可单独重试，已经成功的结果保持不变。

## 4. 发起并监控检测

1. 在“商家”中确认名称、城市、行业和公开来源。
2. 生成问题库，逐条批准或拒绝；只有“已批准且启用”的问题进入检测。
3. 在“检测记录”发起 manual 或 ark 检测。
4. 检测执行中观察成功数与失败数；partial 和 failed 记录仍可打开检查。
5. 完成后进入报告，所有结论都应回到逐题原始回答和来源核验。

## 5. 豆包 App 人工抽查

每次自动检测后，建议选择 10 个代表性问题在豆包 App 中人工复查，记录回答摘要、目标商家是否出现、位置和公开来源。不要记录审核人的姓名、账号、聊天历史或其他个人数据。App 输出可能随时间、账号和上下文变化，人工抽查只作为补充验证。

## 6. 指标口径

- 品牌出现率：有效回答中提到目标商家的比例。
- 首位推荐率：仅在存在明确排序的有效回答中，目标商家位于第一的比例；无排序回答不进入分母。
- 来源覆盖率：有效回答中，目标商家提及同时带有已保存公开来源的比例。
- 待核验：证据置信度不足，只能作为线索，不能写成事实结论。

自动检测结果是公开联网回答的代理指标，不等同于豆包 App 固定排名，也不承诺可以控制平台内部排序。

## 7. 历史对比

第二次检测应尽量沿用相同的问题版本、执行方式和样本规模。在“历史对比”中明确选择左右两次检测，阅读百分点差值。差值描述的是两次样本变化，不证明某次资料修改导致了变化。
