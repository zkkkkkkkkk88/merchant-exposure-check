# 只读演示账号与手机端独立布局设计

## 背景

项目需要交给外部人员向商家现场展示。展示者必须能够浏览已有商家、讲解页面和功能构成，但不能把项目作为自己的业务工具使用，也不能消耗真实检测额度或改变已有业务数据。

当前部署设计只有一组共享入口密码。知道密码的人拥有同等权限，无法区分项目管理员和外部演示者。当前手机端虽然存在响应式规则，但主要沿用桌面端的信息密度、八项导航和多列表格，现场讲解时层级过多、阅读拥挤。

## 目标

1. 建立管理员和演示访客两种访问角色。
2. 演示访客可以浏览完整项目、切换已有商家并讲解已有数据。
3. 演示访客不能创建、修改或删除业务数据，也不能启动任何会消耗额度或产生新结果的任务。
4. 手机端采用独立的信息组织和导航方式，同时保持桌面端现有布局与视觉语言不变。
5. 权限必须由服务端强制执行，不能只依赖隐藏或禁用前端按钮。

## 非目标

- 本阶段不建设开放注册、找回密码、用户管理后台或多租户数据隔离。
- 不建设代理分佣、客户归属和检测额度计费系统。
- 不为每个访客创建独立演示数据副本。
- 不改变现有检测、分析和报告算法。
- 不重新设计桌面端页面。

## 角色与权限

系统提供两个角色：

- `admin`：项目所有者，保留现有完整权限。
- `demo`：外部演示者，全站只读。

| 能力 | admin | demo |
| --- | --- | --- |
| 浏览页面、已有商家和已有结果 | 允许 | 允许 |
| 切换已有商家 | 允许 | 允许 |
| 创建、修改或删除商家 | 允许 | 拒绝 |
| 解析、确认或替换商家画像 | 允许 | 拒绝 |
| 生成或修改问题集 | 允许 | 拒绝 |
| 启动、重试或重新运行检测 | 允许 | 拒绝 |
| 启动平台查缺或采纳平台字段 | 允许 | 拒绝 |
| 创建手机实测轮次、上传证据或确认结果 | 允许 | 拒绝 |
| 查看历史、证据和交付报告 | 允许 | 允许 |

`demo` 的规则是统一禁止所有会改变服务端状态的业务操作。这样不会遗漏未来新增的写入入口，也避免访客通过修改问题、手机实测或平台字段间接污染已有商家数据。

健康检查、页面渲染所需的只读请求以及浏览器自身的非业务请求不受此规则影响。

## 身份识别与请求链路

### 登录入口

延续现有密码保护部署方向，但将单一共享凭据改成两组账号：管理员账号和演示账号。用户名、密码哈希和角色映射只保存在服务端生产环境配置中，不进入 Git、浏览器包或日志。

本地开发默认使用管理员角色，避免影响现有开发流程。测试可以显式注入 `admin` 或 `demo` 身份。

### 可信角色传递

公网请求必须先经过认证入口。入口完成身份校验后，移除任何来自公网的同名角色请求头，再向内部 Web 和 API 服务写入可信角色信息。API、worker 和数据库继续只存在于 Docker 内部网络，不能绕过入口直接从公网访问。

Next.js 服务端操作调用 FastAPI 时必须继续传递当前已认证角色。浏览器不能自行决定或修改角色。

### 服务端授权

FastAPI 提供统一的授权依赖：

- 读取接口允许 `admin` 和 `demo`。
- 写入接口要求 `admin`。
- 身份缺失、无效或角色不允许时返回明确的 `401` 或 `403`。

所有现有写入路由都必须接入该依赖，包括商家、画像、问题集、检测、平台查缺、手机实测、证据上传和确认操作。前端 Server Actions 也要在调用 API 之前检查角色，以便快速返回友好提示；API 检查仍是最终安全边界。

## 演示访客界面

### 可操作状态

演示访客仍能看到项目具有哪些功能。关键写入按钮不完全消失，而是显示锁定或禁用状态，例如：

- 新增商家
- 保存画像
- 生成问题
- 发起检测
- 重试检测
- 开始平台查缺
- 采纳字段
- 保存手机实测

按钮附近或点击反馈统一说明：`当前为演示权限，实际操作请联系管理员。`

不会产生业务写入的浏览交互继续可用，包括导航、切换已有商家、筛选、展开详情、查看证据和切换报告章节。

页面顶部显示低干扰的“演示模式”标识，使讲解者和商家都清楚当前页面不能执行真实操作。

### 错误处理

- 前端已知角色为 `demo` 时，在提交前阻止操作并显示统一提示。
- 如果请求绕过前端到达 API，API 返回 `403`，且不执行任何部分写入。
- 前端收到 `403` 时显示演示权限提示，不展示原始技术错误。
- 身份失效时返回登录入口，不把它误报成数据加载失败。

## 手机端独立布局

手机端断点以现有响应式体系为基础，主要针对不超过 `720px` 的视口。桌面端导航栏、网格和页面结构保持不变。

### 全局导航

手机端采用固定顶部栏和底部主导航：

- 顶部栏：品牌、当前商家简称、`演示模式` 标识。
- 底部主导航：`首页`、`画像`、`检测`、`报告`、`更多`。
- `更多` 面板收纳：平台查缺、问题策略、手机实测、历史和方法说明。

底部导航只改变入口组织，不删除任何页面。当前页面必须有清晰的选中状态，并为正文预留底部安全距离，避免内容被导航遮挡。

### 页面层级

- 页面标题、说明、商家切换器和主要操作在手机端纵向排列。
- 每个首屏只保留一个主要结论和一个主要动作，次要说明下移或折叠。
- 桌面端并排的指标与内容区在手机端改为单列或两列指标卡。
- 全局旅程步骤在手机端压缩为“当前步骤 + 进度”，完整步骤通过展开查看，避免横向滚动长条占据首屏。
- 触控目标最小高度为 `44px`，输入框和主要按钮使用可读的全宽布局。

### 表格与长内容

手机端不再把多列表格简单缩窄或依赖整表横向滚动：

- 商家、问题、竞品、来源差距和平台结果按记录转换为纵向信息卡。
- 卡片顶部展示名称与状态，正文只保留讲解所需的关键字段。
- 次要字段通过“展开详情”显示。
- 原始回答、证据和长说明默认折叠，展开后保持正常换行。
- 必须保持列间比较的少数场景可使用局部横向滚动，但需要固定首列或提供明确提示。

### 页面重点

- 首页：商家结论、核心指标、当前阶段和优先行动先于趋势及完整对比。
- 商家画像：访客以只读信息卡查看；管理员继续使用编辑表单。
- 检测与平台查缺：访客看到流程说明、历史任务和结果，启动按钮显示锁定。
- 手机实测：三道代表题、已有回答和来源证据按轮次折叠，录入区对访客锁定。
- 交付报告：采用适合讲解的章节流，结论、问题、机会和行动建议依次展示。

## 可访问性与视觉延续

- 延续现有深绿色、暖纸色、橙色强调色和衬线标题，不引入新的品牌风格。
- 禁用状态不能只依赖颜色表达；同时使用文字、图标语义和 `aria-disabled`。
- 底部导航、更多面板和折叠内容支持键盘焦点与屏幕阅读器名称。
- 文本和交互控件维持可读对比度，正文不因手机适配缩小到难以阅读。
- 尊重系统安全区域，避免底部导航紧贴设备边缘。

## 数据与安全边界

- 演示账号可以看到系统中允许展示的全部已有商家和报告。本阶段不提供按访客隔离商家的能力。
- 因为访客能看到真实已有数据，管理员应只在系统中保存适合对外展示的商家资料；敏感客户数据不应进入演示环境。
- 只读权限防止新增、修改和额度消耗，但不能阻止访客截图、录屏或复述已经看到的内容。
- 如果未来需要限制不同访客看到不同商家，再增加独立邀请链接和商家白名单；本阶段不提前建设。

## 测试与验收

### 权限测试

- `admin` 可以继续完成现有全部写入流程。
- `demo` 可以加载所有允许展示的页面与已有数据。
- `demo` 对每一种业务写入请求都收到 `403`，数据库不发生变化，后台任务不被创建，外部模型 API 不被调用。
- 伪造角色请求头不能把 `demo` 提升为 `admin`。
- Next.js Server Actions 不丢失当前角色，也不能借助服务端内部地址绕过授权。

### 前端测试

- 管理员看到正常可操作控件。
- 演示访客看到统一的演示标识、锁定控件和权限说明。
- 导航、已有商家切换、详情展开、证据查看和报告章节浏览仍然可用。
- 权限失效与 `403` 使用清晰的中文提示。

### 手机端验证

至少在 `390 × 844` 和 `430 × 932` 两个手机视口验证首页、商家画像、问题策略、检测、手机实测和交付报告：

- 无页面级意外横向滚动。
- 标题、按钮和表单不重叠或被截断。
- 多列表格转换为可读卡片或明确的局部滚动区域。
- 顶部栏和底部导航不遮挡内容。
- 演示模式下所有写入入口均可理解但不可执行。

桌面端至少在 `1440px` 视口完成一次回归检查，确认既有导航和布局未被手机样式影响。

## 实施顺序

1. 建立角色模型、认证入口角色传递和 API 统一授权。
2. 为所有现有写入路由和 Next.js Server Actions 接入权限检查。
3. 增加前端角色上下文、演示标识、锁定控件和统一提示。
4. 调整手机端全局导航与页面布局。
5. 将重点多列表格转换为手机信息卡。
6. 完成权限测试、手机视口视觉验证和桌面回归验证。

权限必须先于手机端视觉调整落地，避免先做出看似受限、实际仍可绕过的演示界面。
