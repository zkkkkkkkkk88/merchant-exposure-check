# 交付报告公开信息渠道维护清单设计

## 目标

在交付报告中把本轮 API 找到的公开来源转化为商家可执行的渠道维护建议。报告既说明回答实际参考了哪些平台，也提示商家还可以维护哪些公开渠道，从而提高后续被检索和正确引用的概率，但不承诺首批推荐。

## 展示位置

功能放在交付报告第 04 部分“公开平台与来源查缺”中，位于现有平台缺口和来源查缺内容之后。该内容保留在网页和打印/PDF 中；只有“原始回答附录”继续在打印时隐藏。

## 数据范围

### 本轮实际引用

- 读取本轮已确认的公开来源。
- 按规范化域名合并重复来源。
- 展示域名、引用次数、来源类型和最多两个代表页面。
- 仅使用真实保存的 URL，不生成或猜测平台链接。

### 候选维护渠道

- 从现有提升方案的 `publishTargets` 中提取渠道并去重。
- 候选渠道与本轮实际引用分开展示，避免把建议渠道误写成已引用来源。
- 没有可靠入口时只展示渠道名称和建议内容，不生成链接。

## 维护权限分级

根据来源已有的 `access_status` 保守映射：

- `maintainable`：可直接维护。
- `correctable`：需要认领或纠错。
- `reference` 或 `unknown`：仅供参考。

报告不得仅凭域名推断商家一定能自行发布。平台能力不明确时统一归为“仅供参考”。

## 界面结构

新增“公开信息渠道维护清单”模块，包含：

1. 一段简短说明：这些来源来自本轮公开信息核对，可用于判断维护优先级。
2. “本轮实际引用”卡片列表：平台域名、引用次数、权限标签、来源类型、代表页面链接。
3. “候选维护渠道”列表：渠道名称及适合补充的内容。
4. “统一信息要求”：商家名称、城市、品类、地址、电话和核心服务保持一致。
5. 边界说明：完善公开信息可提高检索和正确引用概率，但不保证首批推荐。

页面沿用现有交付报告的颜色、边框、字号和间距，不引入新的视觉体系。

## 数据接口

在移动检测工作区响应中新增 `channelMaintenance`：

```ts
{
  citedChannels: Array<{
    domain: string;
    citationCount: number;
    access: "maintainable" | "correctable" | "reference";
    accessLabel: string;
    sourceTypes: string[];
    links: Array<{ title: string; url: string }>;
  }>;
  candidateChannels: Array<{
    channel: string;
    content: string;
  }>;
}
```

后端负责来源聚合、权限标签映射和候选渠道去重；前端只负责展示。没有来源或建议时返回空数组，不让页面报错。

## 异常与边界

- URL 缺失的来源可计入域名统计，但不展示链接。
- 域名缺失且无法从 URL 解析时不进入实际引用清单。
- 同一域名的重复 URL 只展示一次。
- 实际引用为空时展示明确空状态，候选渠道仍可独立显示。
- 所有外链使用新窗口打开，并带安全的 `rel` 属性。

## 验证

- 后端测试覆盖域名合并、引用计数、权限映射、链接去重和候选渠道去重。
- 前端测试覆盖实际引用、权限标签、真实链接、候选渠道、边界说明和空状态。
- 运行完整 Web 测试，并在本地交付报告页面核对桌面布局与打印保留规则。
