# 手机版豆包验证闭环设计

## 目标

把项目从单一的“方舟联网批量检测”升级为双层验证系统：方舟 API 继续承担大批量普查，手机版豆包实测作为最终效果校准。第一版重点降低人工录入成本，并形成目标商家与竞品来源差距的明显对比。

项目不得把方舟结果称为手机版豆包推荐率，也不得承诺任何公开资料建设一定带来推荐提升。

## 第一版范围

第一版包含：

- 从当前已审核问题集中自动抽取 8～15 道代表性手机验证题。
- 用户一次粘贴多条手机版豆包问答，而不是逐题建记录。
- 每轮允许上传少量截图作为证据附件；截图不做 OCR，且不是必填项。
- 每轮保存一份合并来源清单，可直接粘贴豆包追问返回的来源标题、网址或说明。
- 同一批来源无变化时，可以沿用上一轮来源，不要求重复上传“21 篇资料”截图。
- 手机版豆包指标与方舟联网指标分别展示。
- 生成“目标商家与竞品来源差距”主表，主表只使用手机版豆包实测来源；方舟来源保留为辅助信息，不混入主表结论。
- 支持优化前后按相同抽样题集复测并比较结果。

第一版不包含截图 OCR、自动控制豆包 App、录屏解析、自动登录第三方平台或自动发布内容。

## 核心概念

### 手机验证题集

系统从最新已审核且启用的问题集中选择代表题，优先覆盖：

- 泛推荐问题；
- 重点品类或诊疗项目；
- 目标商家品牌验证；
- 竞品或差异比较；
- 方舟结果中未命中或不稳定的问题。

题目不足 8 道时全部选择；题目多于 15 道时最多返回 15 道。相同题集在一次优化前后保持不变，确保可比较。

### 手机实测轮次

一轮实测属于一个商家和一个固定验证题集，保存：

- 测试时间；
- 是否开启联网搜索；
- 测试位置文字；
- 批量粘贴的原始问答文本；
- 每道题的目标商家提及状态与出现层级；
- 回答中识别或人工确认的竞品；
- 本轮合并来源清单；
- 可选截图附件；
- 用户确认状态。

首版不尝试从自由文本中自动推断所有字段。系统提供批量文本作为原始证据，同时让用户用轻量表单确认每道题的“未提及、补充提及、首批推荐”和竞品名称，避免错误自动统计。

### 来源记录

来源按轮次统一保存，而不是每道题重复保存。每条来源包含：

- 标题或域名；
- 可选网址；
- 来源类型：官网/机构介绍、工商、招聘、抖音、本地媒体、政府或医院、行业内容、其他；
- 对应机构；
- 豆包从中采用的可验证事实；
- 证据性质：机构自述、官方/登记信息、第三方内容；
- 可维护状态：可维护、可纠错、仅参照、未知；
- 是否由用户确认。

截图只作为轮次级证据。来源未发生变化时，新轮次可以引用上一轮来源快照；系统必须清楚显示“沿用自哪一轮”。

## 指标口径

页面分成两个独立区域：

### 手机版豆包实测

- 提及率：提及目标商家的有效手机问题数 / 已确认手机问题数。
- 首批推荐率：目标商家进入首批推荐的问题数 / 已确认手机问题数。
- 场景覆盖率：至少一次提及目标商家的问题类别数 / 已测试问题类别数。
- 信息准确率：用户确认无关键错误的提及结果数 / 已确认的提及结果数。
- 来源覆盖率：目标商家拥有已确认来源类型数 / 当前轮次全部出现过的来源类型数。

样本不足或轮次未确认时不计算正式指标，显示“待确认”。

### 方舟联网检测

保留现有指标，但所有页面明确标注为“方舟联网检测”，只用于批量预检和趋势参考，不代表手机版豆包结果。

## 目标商家与竞品来源差距表

主表按来源类型和关键事实维度比较目标商家与本轮实际出现的竞品。典型行包括：

- 官网/机构介绍页；
- 工商或登记信息；
- 招聘页面；
- 抖音公开内容；
- 本地媒体或目录；
- 地址可验证性；
- 电话与营业时间一致性；
- 医生或资质信息；
- 诊疗项目；
- 设备信息；
- 本轮是否被手机版豆包引用。

每个单元格显示“有、缺失、待核对”及简短证据，例如“有：招聘页提及 CT”。缺失仅表示当前手机实测来源中未发现，不断言互联网上绝对不存在。表格突出目标商家相对至少一个竞品缺失的行，并可展开查看来源证据。

竞品集合来自本轮经用户确认的回答，不使用系统预置虚构竞品。方舟引用来源放在表格下方的辅助区域，明确标注“仅供预检参考”。

## 用户流程

1. 用户在商家页面创建手机验证题集，系统给出 8～15 道代表题。
2. 用户在手机版豆包新对话中测试这些问题，并批量复制回答。
3. 用户创建实测轮次，一次粘贴原始问答，填写位置和联网状态。
4. 用户快速确认每题提及层级、竞品和关键信息准确性。
5. 用户一次粘贴合并来源清单；必要时上传 1～3 张来源长截图。
6. 系统计算手机版指标并生成来源差距表。
7. 用户完成公开资料优化后，复制原题集创建复测轮次。
8. 系统比较两轮的提及、首批推荐、准确率以及新增或消失的来源。

## 数据与接口边界

后端新增相互独立的实体：手机验证题集、手机实测轮次、题目结果、轮次来源和证据附件。附件只保存工作区或部署配置指定的文件路径与元数据，不把图片二进制写入数据库。

接口需要支持：

- 为商家生成并读取验证题集；
- 创建、编辑和确认实测轮次；
- 批量保存题目结果；
- 批量保存或沿用来源；
- 上传和读取证据附件；
- 返回手机指标、前后轮对比和来源差距矩阵。

所有读取和写入都必须校验商家归属，不能在商家切换后回退到默认商家。

## 错误与真实性处理

- 没有已审核问题时，提示先生成并审核问题，不生成模拟题。
- 未确认的题目结果不进入正式指标。
- 来源没有网址时允许保存标题，但标记为“待核对”。
- 沿用历史来源必须保留原轮次引用，不复制成伪造的新证据。
- 上传失败不应丢失已填写的问答与来源草稿。
- 不自动把招聘或商家自述当作第三方事实，差距表必须显示证据性质。
- 删除附件仅删除本项目管理的文件，不影响用户原始图片。

## 页面结构

新增“手机实测”导航入口，包含：

- 当前题集与复制按钮；
- 新建实测轮次表单；
- 批量问答文本框；
- 每题快速确认表；
- 合并来源编辑区和可选附件上传；
- 手机版指标卡；
- 醒目的目标商家与竞品来源差距表；
- 优化前后轮次对比。

总览页将现有指标区明确改名为“方舟联网检测”，并在有已确认手机轮次时显示一组独立的手机版实测摘要和入口。

## 验证标准

- 后端测试验证抽样数量、类别覆盖、固定题集复用和无已审核问题的行为。
- 后端测试验证未确认结果不计入指标，以及提及率、首批推荐率和信息准确率口径。
- 后端测试验证来源沿用保持原始轮次、来源性质和商家隔离。
- 后端测试验证差距矩阵只使用手机版来源，并正确标记“缺失”与“待核对”。
- 前端测试验证用户可以批量录入、快速确认、沿用来源和上传可选附件。
- 前端测试验证手机指标与方舟指标不会混合显示。
- 前端测试验证来源差距表突出目标商家相对竞品的明显缺口，并能查看证据。
- 生产构建通过；使用真实商家完成一次不调用付费模型的本地流程验证。
