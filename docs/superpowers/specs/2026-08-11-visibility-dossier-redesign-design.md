# 见序 / Visibility Dossier 产品改造设计

日期：2026-08-11  
状态：已完成需求讨论，待用户复核书面设计

## 1. 背景与目标

现有产品主要用“品牌出现率”和“首位推荐率”描述商家在模型回答中的表现。对于尚未进入推荐的新商家，这两个指标会长期为零，既不能展示公开信息建设的进展，也不能告诉用户下一步应该改善什么。

同时，现有问题生成器直接拼接宽泛行业和固定价格模板。当商家资料不完整时，会生成与真实品类、价格、位置及服务能力冲突的问题。例如西餐厅被归入“餐饮”，双人餐 300–450 元却生成 50 元以内的问题。

本次改造目标是：

1. 把产品从“单纯统计是否被推荐”升级为“帮助商家逐步建立公开可见性”。
2. 建立可解释的成长指标，让尚未被推荐的商家也能看到真实进展。
3. 根据经过确认的商家画像生成精准、自然、无冲突的问题。
4. 保持通用底层能力，通过行业规则包扩展餐饮、酒店、美业和零售等行业。
5. 重构导航和视觉系统，使页面高级、干净、有编辑感，并修复导航选中和返回路径。

## 2. 产品定位与品牌

产品名称改为：

- 中文名称：见序
- 英文副标题：Visibility Dossier

“见序”表达商家从未识别、信息相关、被提及到进入推荐的可见性成长顺序。英文副标题强调产品是一份可追溯、可核验的商家可见性档案。

产品仍面向通用本地生活商家。第一阶段实现餐饮行业规则包，底层画像、问题、检测和指标接口保持行业无关，后续可增加酒店、美业和零售规则包。

## 3. 核心检测模型

### 3.1 双轨检测

每次检测包含两类任务：

1. 推荐检测：使用消费者真实会提出的通用问题，检查目标商家是否被提及或明确推荐。
2. 信息验证：使用商家名称和具体事实进行定向核验，检查价格、位置、服务设施、产品和场景等信息能否从公开来源中被检索、引用和交叉验证。

推荐检测回答“商家现在是否进入推荐”；信息验证回答“商家是否已经具备进入推荐所需的公开信息基础”。两类问题必须在问题库、检测记录和报告中明确标识。

### 3.2 可见性成长阶梯

成长阶段按可验证结果从低到高确定：

1. 未识别：没有可验证的目标商家公开事实，也未在推荐检测中出现。
2. 信息相关：至少一个关键商家事实获得有效公开来源支持，但商家尚未在推荐检测中出现。
3. 被提及：目标商家在推荐类回答中出现，但回答没有明确把它作为推荐对象。
4. 进入推荐：回答明确把目标商家作为满足用户需求的推荐对象。

同一次检测只展示达到的最高阶段，并保留支撑该阶段的回答和来源证据。

“首位推荐率”从界面、API 新版合同和新历史对比中移除。旧数据库字段可暂时保留以兼容历史记录，但不再参与新指标或页面展示。

### 3.3 可见性准备度

可见性准备度为 0–100 的透明组合指标：

- 商家画像完整度：25%
- 公开信息可验证度：35%
- 高意图问题命中：25%
- 同类商家差距收窄度：15%

每项子指标均可展开查看分子、分母、适用字段和支撑证据。不同规则包可以定义适用字段，但不得改变四项总权重，以保证同一商家的历史结果可比较。

直接出现率继续保留为辅助结果指标，不作为准备度的替代值。

## 4. 商家画像

### 4.1 录入流程

1. 用户填写商家名称和城市，并粘贴美团页面文字或其他公开资料。
2. 系统解析候选画像字段，并为每项结果记录来源、解析置信度和待确认状态。
3. 用户逐项确认、修改或删除候选信息。
4. 只有已确认字段可以参与问题生成；待确认字段只用于提示，不得作为事实展示或检测条件。
5. 用户确认完成后生成一个新的、带版本号的问题集。

首版不依赖直接抓取美团页面，避免登录限制、反爬限制和页面结构变化。用户可以粘贴公开页面文字，并补充来源链接。

### 4.2 通用画像字段

- 商家名称、门店名称、城市、行政区、商圈、商场、详细地址和附近地标
- 精准行业与细分品类
- 单人消费、人均消费、套餐价格区间
- 产品、服务、特色优势和适用场景
- 服务设施、交通和停车条件
- 营业时间
- 公开来源及来源类型

画像事实采用可扩展记录结构，而不是为每个行业增加固定数据库列。每条事实至少包含：字段键、结构化值、确认状态、解析置信度、来源链接和最近更新时间。

### 4.3 餐饮规则包字段

- 菜系与餐厅类型
- 人均价格与套餐价格
- 招牌菜和套餐
- 宝宝椅、无烟、明厨亮灶、包间、停车、可预约等设施与服务
- 亲子、约会、朋友聚餐、商务、纪念日等消费场景
- 商圈、商场、地标和交通便利性

## 5. 问题生成策略

### 5.1 行业规则包接口

通用生成引擎调用行业规则包，规则包负责：

- 定义适用画像字段和必填字段
- 定义价格、地域、服务和场景约束
- 生成推荐类与验证类问题候选
- 对问题执行冲突检查和质量评分
- 提供字段缺失提示

以后增加新行业时，只新增规则包和字段配置，不重写问题审核、后台检测、报告或历史对比。

### 5.2 餐饮问题规则

- 精准品类优先：西餐厅不得退化为宽泛“餐饮”。
- 价格必须相交：问题价格区间必须与已确认的商家价格区间相交；没有确认价格时不生成价格问题。
- 地域必须真实：只组合已确认的城市、商圈、商场和地标，避免重复地名。
- 服务与场景必须有依据：只使用用户确认的服务和适用场景。
- 不虚构缺失事实：未知字段不使用默认值补齐。
- 去重与自然语言检查：拦截语义重复、条件堆叠、表达不自然和过宽问题。
- 问题必须记录生成理由、使用的画像字段和所属检测类型。

O'eat Gastronomy 的合格示例包括：

- 杭州万象城有什么值得去的西餐厅？
- 杭州有什么适合带宝宝去的西餐厅？
- 杭州交通方便、适合约会的西餐厅有哪些？
- 杭州双人消费 300–450 元的西餐厅推荐。
- O'eat Gastronomy 是否提供宝宝椅？有哪些公开来源可以证明？

### 5.3 审核与执行

生成后进入人工审核。用户可以编辑、批准、拒绝或启用问题。后台检测只执行“已批准且启用”的问题，并继续使用异步 Worker，避免页面同步等待。

## 6. 报告与历史对比

总览核心显示：

- 当前成长阶段
- 可见性准备度及四项构成
- 商家画像完整度
- 公开信息可验证度
- 高意图问题命中数
- 同类商家差距
- 最优先处理的证据任务

历史对比显示：

- 成长阶段变化
- 准备度及各子指标变化
- 新增或失效的已验证事实
- 高意图问题新增命中和失去命中
- 同类差距变化
- 直接出现率变化，作为辅助数据

报告不得暗示平台内部固定排名，也不得把用户录入但未经公开来源验证的资料当作模型已知事实。

## 7. 页面结构与交互

主导航调整为：

1. 总览
2. 商家画像
3. 问题策略
4. 检测
5. 历史

导航选中状态根据当前路径计算，不再写死“总览”。子页面内容区左上角统一提供返回按钮：优先执行浏览器返回；没有有效历史记录时跳转到预设上级页面。

关键流程为：

商家列表 → 新建或编辑画像 → 确认画像 → 生成精准问题 → 审核问题 → 开始后台检测 → 查看进度 → 查看报告 → 历史对比。

## 8. 视觉方向

采用用户选择的第三套视觉方案：

- 深墨绿色导航、暖白内容表面、陶土色强调
- 餐饮品牌档案与建筑方案册的视觉气质
- 中文衬线展示字体搭配清晰的无衬线正文字体
- 使用排版、留白、细线和数字层级组织信息
- 方角或极轻圆角，避免卡片套卡片
- 不使用渐变、玻璃效果、AI 闪光、表情符号和装饰性仪表盘组件
- 桌面端保持宽阔编辑式网格，移动端转换为顶部导航和单列内容

不使用未经授权的商家照片。若商家没有可用图片，页面保持排版式头部，不使用假照片或占位插画。

## 9. 数据迁移与兼容

- 采用新增表或新增可空字段的非破坏性迁移。
- 现有商家基础字段转换为“待确认”画像候选，不自动认定为已验证事实。
- 旧问题集保持只读和可追溯；新版生成器创建新的版本化问题集。
- 旧扫描结果和原始回答继续可查看。
- 新报告优先读取新指标快照；旧报告显示兼容说明，不伪造缺失指标。
- 不删除旧首位推荐数据，只从新产品体验中隐藏。

## 10. 错误处理

- 解析失败时保留用户粘贴的原文并允许手工填写。
- 画像资料不足时列出缺失字段，不生成虚构问题。
- 单个问题生成失败不影响其他候选，页面显示失败原因。
- 后台检测失败保留已完成结果和队列状态，支持 Worker 恢复后继续执行。
- 指标计算缺少分母时显示“暂无数据”，不显示误导性的 0%。
- 所有保存操作显示进行中、成功或失败状态，失败时回滚乐观更新。

## 11. 验证标准

### 后端

- O'eat 画像不会生成 50、100 或 200 元以内的问题。
- 西餐厅不会生成宽泛餐饮问题。
- 未确认的宝宝椅、无烟、交通等标签不会进入问题。
- 推荐与验证问题均保存类型、生成理由和字段依据。
- 四项准备度子指标和总分计算可复现。
- 成长阶段按证据正确升级，不因单纯用户填写而升级。
- 迁移后旧商家、问题集、扫描和报告仍可读取。

### 前端

- 每条路由显示正确导航选中状态。
- 所有子页面有可用的返回按钮及无历史记录回退路径。
- 画像解析、确认、问题审核、后台检测和报告流程可完整操作。
- 首位推荐率不再出现在新版页面。
- 指标为无数据时不显示误导性的零值。
- 桌面和移动主要布局无溢出，键盘焦点和文本对比度可用。

## 12. 非目标

- 第一版不直接抓取需要登录或受反爬保护的美团页面。
- 第一版不实现餐饮以外的完整行业规则包，只保留扩展接口。
- 不承诺改变豆包内部排名，也不把相关性检测描述为排名优化保证。
- 不自动发布、修改或代替商家维护第三方平台内容。
