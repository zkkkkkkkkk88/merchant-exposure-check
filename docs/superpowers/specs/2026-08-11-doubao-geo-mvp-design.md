# AI 商家曝光检测 MVP 设计

## 1. 项目定位

本项目用于检测本地商家在豆包相关联网搜索场景中的公开信息曝光情况，识别竞争商家、引用来源和信息缺口，并通过历史复测判断公开信息优化是否可能带来曝光改善。

产品不承诺控制豆包内部排名，也不宣称火山方舟联网搜索结果与豆包 App 每次输出完全一致。自动检测是规模化代理指标，豆包 App 人工抽查是补充验证。

第一条演示数据使用 `O'eat Gastronomy（杭州万象城店）`。系统从第一天采用多商家数据结构，不为该商家硬编码规则。

## 2. 第一版目标

第一版需要跑通以下闭环：

1. 创建商家并录入基础资料与公开链接。
2. 自动生成 30 个消费者问题并支持人工审核。
3. 通过可替换的搜索适配器执行联网检测。
4. 保存原始回答、引用来源、目标商家及竞争品牌提及。
5. 计算曝光指标并生成可追溯的信息缺口。
6. 保存不同日期的检测结果并提供历史比较。
7. 支持录入豆包 App 人工抽查结果。

核心验收目标是证明系统能够稳定测出差异、解释差异，并给出有证据支持的可执行建议。

## 3. 第一版非目标

第一版不包含：

- 客户自助注册、组织权限、套餐和支付。
- 自动发布小红书、大众点评、美团或公众号内容。
- 自动联系媒体、达人或顾客。
- 多个 AI 平台的并行监测。
- 对豆包固定排名或曝光提升幅度的保证。
- 微服务、Redis、Celery、向量数据库等非必要基础设施。

## 4. 用户与使用方式

第一版只有单管理员角色。管理员为商家录入资料、审核问题、发起检测、查看报告并录入人工抽查。

底层数据模型支持多个商家。增加新商家只需创建新记录，不需要修改程序。

## 5. 核心业务流程

```text
创建商家
  → 录入事实资料和公开链接
  → 生成问题库
  → 人工审核问题
  → 创建检测任务
  → 执行联网搜索
  → 保存原始回答和来源
  → 结构化识别品牌与提及位置
  → 计算统计指标
  → 生成证据化缺口报告
  → 录入豆包 App 人工抽查
  → 后续复测并比较变化
```

## 6. 技术架构

第一版采用模块化单体：

```text
Next.js 管理后台
        ↓
FastAPI 业务接口
        ↓
PostgreSQL
        ↓
Python 检测任务进程
        ↓
火山方舟联网搜索 / 手动导入适配器
        ↓
结构化提取、统计与报告生成
```

技术选型：

- 前端：Next.js + TypeScript。
- 后端：Python FastAPI。
- 数据库：PostgreSQL。
- 数据处理：Python。
- 模型与搜索：火山方舟 Responses API，封装为可替换适配器。
- 本地运行与首版部署：Docker Compose。
- 任务执行：PostgreSQL 任务表配合独立 Python 进程。

第一版由管理员手动发起检测。自动定时复测在核心闭环验证成功后再加入。

## 7. 组件边界

### 7.1 商家资料模块

负责商家事实资料、核心产品、经营区域和公开来源链接。事实字段与模型推断分开保存。

### 7.2 问题库模块

根据商家行业、地域、产品、价格和消费场景生成问题。每个问题包含分类、优先级、生成原因、审核状态和启用状态。

### 7.3 搜索适配器

定义统一的输入和输出接口。第一版提供：

- 火山方舟联网搜索适配器。
- 手动导入适配器，用于未配置 API 凭据或录入豆包 App 抽查结果。

更换搜索服务不应影响商家、问题库、统计和报告模块。

### 7.4 结果提取模块

把原始回答转换成经过模式校验的结构化数据，包括品牌、提及位置、推荐理由和引用来源。无法确定的字段使用 `unknown`，不得强行补全。

### 7.5 指标模块

只使用确定的结构化结果计算统计指标。指标代码不依赖大模型，保证同一数据得到相同结果。

### 7.6 缺口分析模块

结合目标商家资料、竞争品牌提及和引用来源生成缺口。每项缺口必须关联具体问题、原始结果或来源，并包含置信度。

## 8. 数据模型

### `merchants`

保存店名、城市、区域、行业、地址、价格区间、营业时间、主营产品、核心优势和更新时间。

### `merchant_sources`

保存商家官网、美团、地图、公众号等公开链接及来源类型。

### `query_sets`

保存某个商家的问题库版本和生成时间。

### `queries`

保存问题正文、类别、优先级、生成原因、审核状态和启用状态。

### `scan_runs`

保存一次检测任务的商家、问题库版本、开始时间、完成时间、状态和错误摘要。

### `query_results`

保存每个问题的原始回答、适配器、模型、执行时间、有效状态和结构化提取版本。

### `citations`

保存引用网址、域名、页面标题、摘要及其对应的查询结果。

### `brand_mentions`

保存品牌名称、规范化名称、是否为目标商家、可确认的提及位置和置信度。

### `gap_findings`

保存缺口类型、说明、严重程度、置信度及关联证据。

### `action_items`

保存建议动作、优先级、状态和关联缺口。

### `manual_checks`

保存豆包 App 人工抽查的问题、回答摘要、目标商家是否出现、位置、来源和检查时间。

原始结果不可被分析结果覆盖。算法调整后可以使用历史原始数据重新计算，无需重复调用搜索服务。

## 9. 指标定义

- 品牌出现率：提及目标商家的有效问题数 ÷ 有效问题总数。
- 首位推荐率：目标商家被明确列在第一位的问题数 ÷ 有明确排序的有效问题数。
- 分类覆盖率：目标商家在某类问题中的出现数 ÷ 该类有效问题数。
- 竞争份额：目标商家与主要竞争品牌的有效提及次数对比。
- 独立信源数：支持目标商家的不同有效域名数量。
- 信源覆盖率：存在目标商家支持来源的问题数 ÷ 有效问题总数。
- 信息完整度：地址、价格、营业时间、产品等事实字段的已确认覆盖比例。
- 结果波动率：同一问题重复检测时，品牌集合或顺序发生变化的比例。
- 任务有效率：得到可分析结果的问题数 ÷ 本次执行的问题总数。

回答没有明确排序时不计算前三推荐，只记录提及和能够确认的出现顺序。

## 10. 页面结构

### 10.1 仪表盘

展示商家切换、最近检测状态、品牌出现率、首位推荐率、分类覆盖、主要竞争对手、高优先级缺口和最近两次检测变化。

### 10.2 商家资料

编辑商家事实资料和公开链接，并显示信息完整度、字段冲突、缺失信息和最近更新时间。

### 10.3 问题库

按类别查看问题，支持生成、审核、编辑、启停和批量选择，并展示每个问题的生成原因。

### 10.4 检测任务

展示进度、成功数、失败数、待处理数、原始回答、目标商家出现情况、竞争品牌、引用来源及单个失败问题的重新执行入口。

### 10.5 分析报告

按“问题—证据—建议”组织内容。结论可以展开到对应的原始回答、来源和统计口径。

### 10.6 历史对比

比较两个检测日期的总体指标、问题类别、竞争品牌和信源变化。

## 11. 仪表盘视觉规范

界面采用成熟数据产品的编辑式视觉语言，不使用常见的“AI 工具模板感”。

### 视觉原则

- 克制、清晰、可信，优先呈现数据关系而不是装饰。
- 使用暖白或浅灰背景、深灰正文和单一品牌强调色。
- 不使用大面积紫蓝渐变、发光边框、玻璃拟态、机器人图标或星光装饰。
- 不把每段内容都放进独立圆角卡片，优先使用分区、细分隔线、表格和留白建立层级。
- 圆角保持适中，阴影轻微或不用阴影。
- 数字使用易比较的等宽数字样式，图表避免彩虹配色。
- 动效只用于任务进度、筛选反馈和数据切换，不使用无意义漂浮动画。

### 页面布局

- 左侧为窄导航，顶部提供商家切换和检测操作。
- 首屏用一条简洁的指标带展示关键数字，不堆叠巨大统计卡。
- 中部以曝光趋势和分类覆盖为主，竞争品牌对比放在同一视觉轴线上。
- 右侧或下方展示有证据支持的优先行动，避免聊天气泡式 AI 建议。
- 报告文字使用报告编辑排版，明确区分事实、推断和建议。

### 文案风格

- 使用“检测”“证据”“变化”“建议”等业务词汇。
- 避免“AI 洞察”“智能魔法”“一键增长”等空泛表达。
- 不把模型置信度包装成确定事实。

## 12. 异常与安全

- API 密钥只存在服务端环境变量，不写入数据库、日志或前端包。
- 外部网页、搜索结果和导入内容全部视为不可信数据，不能覆盖系统指令或分析规则。
- 模型输出必须通过 JSON 模式与字段校验。
- 单个问题失败不会使整批任务失败。
- 遇到限流时延迟重试；同一外部操作连续失败两次后停止自动重试并显示原因。
- 无来源、疑似同名品牌或无法确认顺序时标记为不确定。
- 原始事实、自动提取、人工修正和模型推断分别记录。
- 报告固定展示“自动检测结果不等同于豆包 App 固定排名”的说明。

## 13. 验证与测试

### 单元测试

- 指标公式和边界条件。
- 品牌名称规范化和同名处理。
- 结构化结果模式校验。
- 历史比较计算。

### 集成测试

- 从商家创建到检测报告的完整流程。
- 搜索适配器成功、限流、超时和无来源响应。
- 部分问题失败时任务仍可完成。
- 原始数据重新分析不会触发新的搜索调用。

### 演示验收

1. 创建 O'eat 商家档案。
2. 生成并人工审核 30 个问题。
3. 完成一次自动检测。
4. 检查品牌识别、竞争品牌和来源提取。
5. 人工在豆包 App 抽查其中 10 个问题。
6. 对比自动检测和人工结果。
7. 确认每条缺口建议均有关联证据。
8. 创建第二次检测并正确展示历史变化。

## 14. 完成标准

- 30 个问题可以完整保存和执行。
- 部分问题失败不会破坏整次任务。
- 指标可以从原始数据确定性重算。
- 竞争品牌识别结果支持人工修正。
- 所有建议可追溯到具体证据。
- 两次检测结果可以正确比较。
- 无法确认的内容不会展示为确定事实。
- 仪表盘符合克制、成熟、非模板化 AI 风格的视觉规范。

## 15. 后续阶段

只有第一版核心闭环通过真实数据验证后，才考虑定时复测、客户账号、套餐计费、多平台监测、内容生成和发布协作。
